The V3 one-way door

EasyEDA V3 rewrites a project's file format the first time it saves, and a V2.2 client can never open it again. This is what that costs, what it buys, and the order of operations that keeps every rollback available.

Verdict: the upgrade is real and available, but it is not the decision to make first. Two things must happen regardless of whether we ever upgrade — and one of them is already exposed today.

Where the versions actually stand

What we run
2.2.40.8
Desktop client and editor core. Built 15 Jul 2025 — about 13 months old. Not offered anywhere by the vendor; the archive jumps to 2.2.47.7.
What is current
3.2.149
Desktop, including macOS Apple-silicon. V3.2 shipped 1 Jun 2026. The web editor at pro.easyeda.com already serves V3.2.148.
What the ecosystem targets
~3.2
easyeda-agent's connector and the marketplace build against the 3.2 extension API. Our bridge was validated against 2.2.40.8 behaviour.

Our 2.2.40.8 bundle has now been archived to SpectraSynq-EDA/_archive/easyeda-clients/ — before this it existed in exactly one place on earth, /Applications, with no way to obtain it again.

The mechanism that makes this irreversible

"V3 features a completely new file format. After you open and save legacy projects in V3, project files will be upgraded automatically. These upgraded files cannot be opened with V2.2, since the two versions use incompatible file structures." EasyEDA Team — V3.2 release notice, 1 Jun 2026

Two things that are true right now

1. The hazard is already live, with nothing installed

The web editor at pro.easyeda.com serves V3.2 today, and it reaches the same cloud projects as the desktop client. Opening K1 there and letting it save migrates the project — no download, no install, no warning from us. Autosave means "open" and "save" are effectively the same act.

Until backups exist, production projects should be opened only in the 2.2.40.8 desktop client.

2. Our measuring instrument is broken

The bridge's own get_capabilities currently reports 87 of 90 methods unsupported and the dmt_*, sch_* and pcb_* mounts missing. Minutes later list_project_objects — which that report calls unsupported for want of dmt_Board — returned the complete, correct project tree.

The probe emits false negatives. That matters far beyond tidiness: it is precisely the instrument we would use to answer "does V3 still expose what we need?" A migration cannot be validated with an oracle that cannot pass a positive control.

Correction to the 28 Aug trial finding

Yesterday's conclusion — that the easyeda-agent connector is inert because a 3.2-era bundle is refused by a 2.2 loader — does not survive checking. The working Run API Gateway declares the same engines.eda ~3.2.0 and the same @jlceda/pro-api-types ^0.2.21 as the dead connector, on this same host, and the packaged .eext contains a well-formed dist/index.js.

The surviving hypothesis is narrower and cheaper: the connector's activate() reaches for eda.sys_Storage, sys_I18n and sys_Log before it ever dials, and an unguarded call to a mount this build lacks throws silently — menus registered, module dead. That is the documented F96 failure class, and if it holds, a guard patch fixes the connector on 2.2.40.8 with no upgrade at all.

The capability probe in Phase 1 answers this as a by-product. The upgrade decision should not be made on yesterday's reasoning.

Order of operations

P0

Fence and freeze

Export every project — cloud and offline — to local .epro / .elibz, checksum them, and prove each one restores by reimporting into a scratch project on the current client. An unverified backup is not a backup. Record the project and document UUIDs so provenance can be remapped later. Archive the client bundle and its user-data directory with the app closed. Disarm every auto-connecting daemon for the window.

no install fully reversible GATE: every export reimports clean
P1

Repair the instrument

Build a read-only capability probe that enumerates the live eda.* surface and emits a capability manifest. It ships only once it is fault-evident: a known-present mount must read present, a fabricated mount name must read absent, and its verdict must match observed tool behaviour across a sample of methods. Then fix or replace get_capabilities so the bridge stops lying. By-product: the exact list of mounts 2.2.40.8 lacks, which settles the connector question.

read-only GATE: probe goes red on an injected fault answers the connector question
P2

Characterise V3 in isolation

Install 3.2.149 beside the current client — different bundle path, separate user-data directory — and point it only at throwaway projects. Run the same probe to produce a V2↔V3 capability delta. Establish empirically whether opening alone migrates or only saving does, using a disposable subject. Expect our CDP automation to break here: V3 moves the extension manager to Advanced and adds a script manager.

scratch projects only GATE: delta matrix published before any rework
P3

Re-architect for version portability

Every tool declares the mounts it needs; dispatch resolves them against the live probe manifest at handshake and fails closed, by name, when one is absent — never silently degrading. Add a differential harness that runs the same operation on both hosts and compares the emitted artefacts — netlist, document source, Gerber — not the return flags. 2.2.40.8 stays the reference implementation until that harness is green.

2.2.40.8 stays primary GATE: differential harness green on both hosts
P4

Rehearse the rollback, then decide

Clone a real project, migrate the clone, run the full pipeline on V3, then execute the documented rollback end to end and verify the restored copy against its checksums. A rollback that has never been performed does not exist. Only after a clean rehearsal does cutover become a decision rather than a gamble.

first migration of real data GATE: rehearsed restore verified against checksum

The point of no return

One line, one moment
The first save of a production project under V3.
Everything before it is reversible. Nothing after it is, except from the backups taken in P0.

What the red team found

SeverityFailure modeWhy the obvious plan misses it
CRITICAL Binary rollback mistaken for data rollback The project lives in JLC's cloud, not in the app. Reinstalling 2.2.40.8 restores the tool and not the file it can no longer open.
CRITICAL Autosave performs the migration for you "Just open it and look" is not read-only. The editor autosaves, and our own agent daemon shipped with a 3-second autosave debounce.
CRITICAL Validating with a broken oracle get_capabilities already reports working mounts as missing. Used as the migration gate, it would condemn a healthy host — or bless a broken one.
HIGH Restore breaks the evidence chain Reimport mints new UUIDs, but EASYEDA-MUTATION-STATE.json, the mutation ledger and evidence manifests are keyed to the old ones.
HIGH Source-hash gating assumes the V2 format Transaction gating rests on get_document_source and expectedSourceHash. A new on-disk representation changes what those hash.
HIGH Our exact build is unobtainable The vendor archive offers 2.2.47.7 and 2.1.64 — not 2.2.40.8. Losing the bundle loses the only host our bridge was validated against. Now archived.
MEDIUM Mixed-fleet drift One account, one cloud. Running both clients means any project opened under V3 converts silently while the other half of the work still expects V2.
MEDIUM Staying put is not free 13 months stale and widening. Every third-party extension will keep failing the way the connector did, and each diagnosis costs a session.

The decision

A

Hold on 2.2.40.8 — run P0 and P1 now Recommended

Backups, archived client, working capability probe. Costs no upgrade risk, removes the live hazard, and very likely fixes the connector on the current host as a by-product. Everything after stays optional.

B

Commit to the full migration, P0 through P4

Buys the 3.2 ecosystem, native version control with branch switching, and native APIs that replace hand-rolled bridge methods. Costs real engineering on the bridge and a rehearsed cutover. Reasonable — but only after P1, since the delta cannot be measured until the probe works.

C

Defer the upgrade question entirely

Legitimate. P0 is still mandatory: the web editor is already V3 and reaches the same projects, so the exposure exists whether or not we ever install anything.

Default if nothing is said: P0 and P1 proceed, nothing is installed, no production project is opened outside the 2.2.40.8 client, and the upgrade decision waits for the capability delta.
